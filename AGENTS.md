# AshEvents - AI Assistant Guide

**AshEvents** is a Spark extension for the Ash Framework. It records create, update and destroy actions as events (with actor attribution, changed attributes and metadata) and can rebuild resource state by replaying them, with version-based replay overrides for schema evolution.

- **Stack**: Elixir ~> 1.15, Ash ~> 3.33, Spark, PostgreSQL via AshPostgres (tests)
- **This guide is for working on AshEvents itself.** How to *use* AshEvents in an app (setting up an event log, tracking actions, replay, version management, side effects) is documented in [usage-rules.md](usage-rules.md) and [README.md](README.md). Read those when you need user-facing behaviour, and keep them in sync when you change it.

## Rules

1. **Read before changing.** Read the relevant core files (see the map below) before any non-trivial change.
2. **Never edit `documentation/dsls/`.** It is generated by `mix spark.cheat_sheets` (and checked by `mix check`); change the DSL docstrings in `lib/` instead.
3. **Set an actor in tests** for every action that records an event (`Ash.create!(changeset, actor: user)`), unless the test is about missing actors.

## Commands

Use `mix test.reset`, not `mix ecto.reset`, to reset the test database.

```bash
mix test.reset                    # drop, create and migrate the test database
mix test                          # run the suite (about 165 tests)
mix test.generate_migrations      # generate migrations after changing test resources
mix test.check_migrations         # verify migrations are up to date
mix check                         # everything CI runs: compile, format, credo, spark checks, REUSE, tests, ...
mix format && mix credo --strict
mix dialyzer
mix docs                          # also regenerates documentation/dsls/
mix sync_usage_rules              # regenerate Claude skills from deps' usage rules
```

## Dependency Skills

Claude skills generated from the usage rules of the deps this library builds on live in `.claude/skills/` (`use-ash`, `use-spark`, `use-ash-postgres`). They are gitignored and generated locally by `mix sync_usage_rules`, as configured in `usage_rules/0` in [mix.exs](mix.exs). Run it after `mix deps.get` in a fresh clone or when deps change; the worktree setup script runs it for you.

## Worktrees

Every git worktree gets its own test database and tidewave port.

**Create**:
```bash
git worktree add <path> -b <branch>
<path>/scripts/worktree-setup.sh <path>
```
Worktree tooling may already run [scripts/worktree-setup.sh](scripts/worktree-setup.sh) for you; if `mise.local.toml` is missing in the worktree, run it yourself. It is safe to re-run.

**Tear down**:
```bash
<path>/scripts/worktree-teardown.sh <path>   # drops the worktree's test database
git worktree remove <path>
```

**Test database isolation depends on mise**: `POSTGRES_TEST_DATABASE` is only set in shells where mise is activated, or for commands run with `mise exec --`. If it is unset, tests fall back to the shared `ash_events_test` database. In a worktree, check with `echo $POSTGRES_TEST_DATABASE` before running `mix test.reset`, and use `mise exec -- mix test` if it is empty.
